Статус: решения Этапа 0

## Как читать документ

Все решения ниже выбраны как безопасные и по возможности обратимые. Статусы:

- **Принято** — действует для MVP;
- **Временно** — допустимо только в явно указанном этапе;
- **Отложено** — интерфейс или граница предусмотрены, реализация не заявляется.

Изменение принятого решения оформляется новой записью: старую запись не удаляем, а помечаем заменённой. Необратимая миграция данных, платная операция, внешний credential или юридический выбор требуют отдельного подтверждения владельца продукта.

## ADR-001. Модульный монолит Next.js

Статус: **Принято**

Контекст: MVP охватывает авторизацию, AI, редактор, публикацию и позднее формы/оплату/домены, но команда и нагрузка не оправдывают распределённую систему.

Решение: один Next.js App Router application, один репозиторий и одна PostgreSQL-база. Доменные модули отделены импортами и прикладными сервисами, но развёртываются совместно.

Последствия:

- проще локальный запуск, транзакции, тестирование и восстановление;
- нет сетевой согласованности и отдельной observability для микросервисов;
- запрещены прямые импорты Prisma и provider SDK из UI;
- при реальной необходимости модуль можно выделить позже по уже существующему интерфейсу.

Обратимость: высокая; provider/module boundaries создают seam для последующего выделения.

## ADR-002. Server-first App Router и явные HTTP-границы

Статус: **Принято**

Контекст: Next.js имеет несколько вызываемых серверных входов. Одного redirect/proxy недостаточно для авторизации.

Решение: чтение по умолчанию выполняется серверными компонентами через DAL. Server Actions применяются к browser-owned mutations, Route Handlers — к Better Auth, публичным endpoints, uploads, webhooks и machine-to-machine вызовам. Любая такая функция рассматривается как публичный endpoint и сама проверяет auth, ownership, Zod и rate limit.

Последствия: меньше client bundle и утечек DTO; проверки могут повторяться, но централизованы. Client Component получает только нужные поля.

Обратимость: высокая; use case не зависит от транспорта и может быть вызван другим adapter.

## ADR-003. PostgreSQL + Prisma, JSONB только для валидируемых снимков

Статус: **Принято**

Контекст: PageSchema меняется как агрегат, а пользователи и связи требуют реляционных ограничений.

Решение: нормализованные сущности и ownership — реляционные таблицы; Page draft/published/version и ограниченные конфигурации — PostgreSQL JSONB. Любое чтение/запись JSONB проходит versioned Zod.

Последствия: snapshot publish и rollback просты; произвольный JSON нельзя считать доверенным. По полям, требующим поиска/unique/FK, данные выносятся в колонки, а не запрашиваются глубоко в JSON.

Обратимость: средняя; JSON schema мигрируется чистыми функциями, реляционные изменения — Prisma migrations.

## ADR-004. Better Auth вместо собственной криптографии

Статус: **Принято**

Контекст: ТЗ требует email/password, verification, reset и серверные сессии.

Решение: Better Auth с официальным Prisma adapter и его актуальной сгенерированной схемой. Собственные password hashing/token/session algorithms запрещены. Сессия хранится в БД; cookie не расширяется на пользовательские публичные поддомены.

Последствия: auth schema сверяется при обновлении зависимости; email sender остаётся заменяемым. Социальные логины, magic link, телефон и 2FA не включаются в MVP.

Обратимость: средняя; доменная User ссылается на стабильный user id, auth детали изолированы в модуле.

## ADR-005. Централизованная ownership-проверка в DAL

Статус: **Принято**

Контекст: знание Project id не должно давать доступ.

Решение: каждый приватный запрос начинается с серверной сессии и запроса Project по составному predicate `id + userId`. Вложенные ресурсы доступны только через Project relation. DTO не содержит encryptedConfig, session token или лишние персональные данные.

Последствия: проверки обязательны даже после UI guard. Чужой и отсутствующий ресурс отвечают одинаково. Тест ownership обязателен для каждого use case.

Обратимость: высокая; policy/DAL можно усилить организационными ролями позднее.

## ADR-006. PageSchema v1 и закрытый renderer

Статус: **Принято**

Контекст: исполнение AI/user code создаёт неприемлемый XSS/RCE риск.

Решение: данные соответствуют `schemaVersion: 1`, строгим схемам page/theme/SEO/button/link/form и discriminated union 15 block types. Renderer использует статический registry заранее написанных React-компонентов.

Запрещено: raw HTML, raw CSS, JS, eval/new Function, iframe, data URL, dynamic module import и выбор DOM tag пользователем.

Последствия: меньше свободы, зато предсказуемая адаптивность, CSP, SEO и миграции. Новый block/variant добавляется кодом и тестами.

Обратимость: высокая на уровне данных благодаря schemaVersion/migration registry; снятие запрета на код не планируется.

## ADR-007. Двухэтапная очистка и строгая валидация JSON

Статус: **Принято**

Контекст: требуются одновременно удаление неизвестных полей и строгая canonical schema.

Решение: untrusted JSON сначала ограничивается по размеру и проецируется рекурсивным allowlist sanitizer, затем canonical объект валидируется Zod strict и domain invariants. Для AI допустим один repair; вторая ошибка завершает операцию без записи.

Последствия: неизвестные поля не переживают boundary, но и не маскируют ошибку в сохранённом объекте. Один pipeline используется для mock и production AI.

Обратимость: высокая; sanitizer/parser можно заменить при сохранении тестового контракта.

## ADR-008. Полностью раздельные draft и published snapshots

Статус: **Принято**

Контекст: правки редактора не должны менять работающий сайт.

Решение: editor читает/пишет только `draftSchema`; public resolver читает только `publishedSchema` и требует `publishedAt`. Publish внутри одной DB transaction валидирует draft, создаёт PageVersion и копирует canonical JSON.

Последствия: публикация требует дополнительного места, зато не имеет «протекания» черновика и легко тестируется. Никакого fallback published → draft.

Обратимость: низкая намеренно: граница является продуктовой и security-гарантией. Формат snapshot версионируется.

## ADR-009. Ограниченные AI patch operations

Статус: **Принято**

Контекст: свободный merge patch позволяет изменить типы, id или служебные поля.

Решение: только updateBlock/addBlock/removeBlock/moveBlock/updateSiteTheme/updateSeo. Изменения проходят operation schema, применяются к копии актуального draft и затем валидируются как полная PageSchema. `id/type/schemaVersion` и ownership не меняются через partial changes.

Последствия: меньше неоднозначности; сложная команда раскладывается в массив проверяемых операций. Перед крупным patch создаётся version.

Обратимость: высокая; union можно расширять совместимыми operation types.

## ADR-010. LLMProvider и честный MockLLMProvider

Статус: **Принято** для интерфейса, **Временно** для mock

Контекст: разработка не должна зависеть от ключей или стоимости внешней модели.

Решение: business layer знает только LLMProvider. Этап 1 выбирает `LLM_PROVIDER=mock`; mock детерминированно строит валидный русский PageSchema из локальных шаблонов и проходит production validation pipeline.

Mock явно не умеет:

- обращаться к реальной модели или обещать качество GigaChat;
- давать достоверные tokens/cost;
- streaming и обобщённое понимание любого запроса;
- незаявленные AI edit operations.

Неподдержанная операция возвращает typed `PROVIDER_CAPABILITY_UNAVAILABLE`, а не фальшивый успех.

Последствия: вертикальный сценарий воспроизводим без credential. GigaChat подключается отдельным adapter после выдачи ключа и contract tests.

Обратимость: высокая; provider выбирается environment config.

## ADR-011. Глобально уникальный slug

Статус: **Принято**

Контекст: slug используется и в `/s/{slug}`, и в будущем `{slug}.{rootDomain}`.

Решение: lowercase ASCII slug, зарезервированные системные имена запрещены, уникальность обеспечивается БД. Коллизия решается понятным суффиксом и может быть вручную изменена владельцем с повторной проверкой.

Последствия: URL однозначен без user namespace. Изменение slug меняет публичный URL; redirect со старого slug — отдельная будущая функция.

Обратимость: средняя; переход на composite namespace потребует route/data migration.

## ADR-012. Optimistic revision для черновика

Статус: **Принято**

Контекст: autosave, две вкладки и медленный AI могут перезаписать свежие изменения.

Решение: Page имеет монотонный `draftRevision`. Любая mutation передаёт expected revision и обновляет строку условно; конфликт возвращает 409 и не делает last-write-wins молча.

Последствия: UI должен предложить перезагрузить/сравнить версию. Для Этапа 1 это простая проверка, на Этапе 2 основа autosave/undo.

Обратимость: высокая; revision можно дополнить operation log, не ломая snapshot.

## ADR-013. Интерфейсы инфраструктурных провайдеров

Статус: **Принято**

Контекст: локальная разработка и российский production используют разные сервисы.

Решение: LLM, Storage, Image, Email, Billing, DomainInfrastructure и DomainRegistrar представлены узкими server-only интерфейсами. Provider выбирается валидированной env-конфигурацией. Неизвестное значение не делает silent fallback на mock в production.

Последствия: mocks возможны без лжи; credential не проходят в domain/UI. Provider-specific error преобразуется в стабильный код.

Обратимость: высокая; adapters заменяемы.

## ADR-014. Один VPS, Docker Compose и Caddy

Статус: **Принято**

Контекст: ТЗ фиксирует Timeweb Cloud, Москва, Ubuntu LTS и отсутствие Kubernetes.

Решение: Caddy, Next.js и PostgreSQL — отдельные контейнеры в private network. Снаружи открыты только 80/443. Persistent DB volume, healthchecks, restart policy, log rotation и внешние зашифрованные backups обязательны.

Последствия: понятная и недорогая эксплуатация; single-host остаётся точкой отказа до следующего масштаба. Managed DB не требуется.

Обратимость: высокая для web/storage, средняя для переноса DB; стандартные image/PostgreSQL/S3 не привязаны к облаку.

## ADR-015. Correctness-first cache

Статус: **Принято**

Контекст: ошибка кеша не должна смешать draft/published.

Решение: Этап 1 может обходиться без application cache. Позднее кешируется только published snapshot с ключом revision/timestamp; invalidation выполняется после commit. Ограниченный TTL служит страховкой.

Последствия: первый прототип делает больше DB reads, но сохраняет правильность. Draft никогда не попадает под public cache key.

Обратимость: высокая; cache — adapter над public resolver.

## ADR-016. Мягкое снятие с публикации

Статус: **Принято**

Контекст: удаление последнего publishedSchema делает действие труднообратимым.

Решение: unpublish устанавливает `publishedAt = null` и закрывает resolver, но сохраняет последний published snapshot и PageVersion. Новая публикация всё равно берёт текущий draft.

Последствия: быстрое восстановление и аудит; занятое место невелико. Retention старых versions задаётся отдельно.

Обратимость: высокая; snapshot можно удалить позже только утверждённой retention-политикой.

## ADR-017. Явные ограничения Этапа 1

Статус: **Временно**

Контекст: Этап 1 обязан доказать вертикаль, а не подделать готовность последующих модулей.

Решение:

- реализуются главная, регистрация/вход, создание Project/Page, MockLLM generation, простой editor, publish и `/s/{slug}`;
- console email помечается local-only и не считается доставкой;
- form block может только отображаться с явным disabled/demo состоянием до Этапа 3;
- нет реальных GigaChat, uploads/S3, AI edits, Telegram, Метрики, ЮKassa, DNS, custom domain или REG.RU;
- нет обещаний production multi-instance rate limit, backup/restore и SSL automation до hardening;
- UI не показывает успешный результат несуществующей операции.

Последствия: демо честно и тестируемо; полные критерии MVP достигаются последующими этапами.

Обратимость: полная; ограничения снимаются отдельными проверяемыми vertical increments.

## ADR-018. Расширяющие миграции и обратимый deploy

Статус: **Принято**

Контекст: откат образа опасен, если новая миграция уже удалила старые поля.

Решение: schema changes по схеме expand → deploy совместимого кода → backfill/verify → отдельный contract позднее. Backup создаётся и проверяется до рискованной миграции. Образ имеет immutable tag; migration запускается отдельным job.

Последствия: некоторые изменения требуют двух релизов и временной дубликации, но rollback остаётся возможным.

Обратимость: высокая до отдельного contract-релиза; contract требует явного подтверждения и свежего restore test.

## Отложенные решения

До получения реальных credential или юридического заключения не фиксируются:

- конкретные GigaChat model id, quota и стоимость;
- SMTP-провайдер и политика доставляемости;
- YooKassa production account и окончательная схема чеков/налогов;
- юридические retention-сроки заявок, audit и удалённых аккаунтов;
- точная политика трансграничной обработки;
- production DNS/ACME параметры и wildcard certificate;
- API покупки доменов REG.RU.

До решения этих вопросов используются только выключенные feature flags или явно подписанные local mocks. Это не блокирует безопасную реализацию Этапа 1.
